# User APIs

## Purpose

Implement the first set of ApeWada backend APIs for **user registration, authentication, profile management, and user-related operations**.

The backend uses:

- Node.js
- Express.js
- TypeScript
- PostgreSQL
- JWT authentication
- REST APIs

Do **not** implement job, worker request, booking, chat, review, or notification APIs in this task.

The goal of this task is to establish a clean and reusable user/authentication foundation for the rest of the ApeWada backend.

---

# 1. User Roles

ApeWada has three user roles:

```text
CUSTOMER
WORKER
ADMIN
```

For the first implementation:

- Customers can register normally.
- Workers can register normally but their worker profile requires admin approval before becoming publicly visible.
- Admin accounts are not created through the public registration API.
- Admin accounts should be created through a secure seed/script or manually in the database.

# 3. User Registration

## Endpoint

```http
POST /api/auth/register
```

The API must support:

```json
{
  "name": "John Doe",
  "email": "john@example.com",
  "phone": "+94771234567",
  "password": "Password123!",
  "role": "CUSTOMER",
  "preferredLanguage": "EN"
}
```

For worker registration:

```json
{
  "name": "Kamal Perera",
  "email": "kamal@example.com",
  "phone": "+94771234567",
  "password": "Password123!",
  "role": "WORKER",
  "preferredLanguage": "SI"
}
```

---

# 4. Registration Rules

Validate all registration requests.

### Required fields

```text
name
email
phone
password
role
preferredLanguage
```

### Name

- Must not be empty.
- Trim leading/trailing whitespace.
- Minimum length: 2 characters.
- Maximum length: 100 characters.

### Email

- Must be a valid email address.
- Normalize email to lowercase.
- Must be unique.

### Phone

- Must be a valid phone number.
- Store phone numbers consistently.
- Prefer E.164 format where possible.

Example:

```text
+94771234567
```

### Password

- Minimum 8 characters.
- Never store the plain-text password.
- Hash the password using a secure password hashing algorithm such as Argon2id or bcrypt.

### Role

Only allow:

```text
CUSTOMER
WORKER
```

Do NOT allow:

```text
ADMIN
```

through the public registration API.

### Language

Only allow:

```text
EN
SI
```

---

# 5. Registration Transaction

Registration must be atomic.

For a customer:

```text
BEGIN TRANSACTION

Create users record
        ↓
Create customer_profiles record

COMMIT
```

For a worker:

```text
BEGIN TRANSACTION

Create users record
        ↓
Create worker_profiles record
        ↓
Set approval_status = PENDING
        ↓
Set availability_status = UNAVAILABLE

COMMIT
```

If any operation fails, roll back the complete transaction.

Do not create a user without the corresponding role-specific profile.

---

# 6. Worker Approval

Worker registration must NOT automatically make the worker publicly available.

New workers should have:

```text
approval_status = PENDING
```

The worker should not appear in public worker search until an admin approves the profile.

Admin approval APIs are outside this task and will be implemented separately.

# 8. Login

## Endpoint

```http
POST /api/auth/login
```

Request:

```json
{
  "email": "john@example.com",
  "password": "Password123!"
}
```

The login API should:

1. Validate request.
2. Find user by normalized email.
3. Verify password.
4. Check that the account is active.
5. Update `last_login_at`.
6. Generate JWT access token.
7. Return authenticated user information.

Example response:

```json
{
  "success": true,
  "message": "Login successful",
  "data": {
    "user": {
      "id": "uuid",
      "name": "John Doe",
      "email": "john@example.com",
      "phone": "+94771234567",
      "role": "CUSTOMER",
      "preferredLanguage": "EN"
    },
    "accessToken": "jwt-token"
  }
}
```

Never return the password or password hash.

---

# 9. JWT Authentication

Create reusable authentication middleware.

Example:

```text
authenticate
```

The middleware must:

1. Read the `Authorization` header.
2. Expect:

```http
Authorization: Bearer <token>
```

3. Validate the JWT.
4. Extract the user ID and role.
5. Verify the user still exists and is active.
6. Attach authenticated user information to the request.

Example:

```typescript
req.user = {
  id: userId,
  role: userRole,
};
```

The JWT payload should contain only necessary information.

Example:

```json
{
  "sub": "user-uuid",
  "role": "CUSTOMER"
}
```

Do not put sensitive information into the JWT.

---

# 10. Role Authorization Middleware

Create reusable middleware for role-based authorization.

Example:

```typescript
authorizeRoles("CUSTOMER");
```

or:

```typescript
authorizeRoles("ADMIN");
```

or:

```typescript
authorizeRoles("CUSTOMER", "WORKER");
```

The middleware must reject unauthorized roles with:

```http
403 Forbidden
```

Authentication failure should return:

```http
401 Unauthorized
```

# 15. Change Password

## Endpoint

```http
PATCH /api/users/me/password
```

Authentication required.

Request:

```json
{
  "currentPassword": "OldPassword123!",
  "newPassword": "NewPassword123!"
}
```

Process:

1. Validate current password.
2. Validate new password.
3. Hash the new password.
4. Update `password_hash`.
5. Return success response.

Never return the password or password hash.

Consider invalidating existing sessions/tokens after password change if refresh-token/session management is introduced.

# 17. Profile Image

Profile images will be stored in Supabase Storage.

Do not store image binary data in PostgreSQL.

PostgreSQL should store only the storage path:

```text
avatar_path
```

The profile-image upload implementation should:

1. Authenticate the user.
2. Validate file type.
3. Validate file size.
4. Upload the file to Supabase Storage.
5. Store the resulting storage path in `users.avatar_path`.

Suggested storage path:

```text
profiles/{userId}/avatar/{filename}
```

If the image upload API requires a separate endpoint, use:

```http
POST /api/users/me/avatar
```

# 18. User Deactivation

## Endpoint

```http
PATCH /api/users/me/deactivate
```

Do not physically delete the user account immediately.

Set:

```text
is_active = false
```

The backend should prevent inactive users from logging in or accessing protected APIs.

Important historical records such as jobs, bookings, cancellations, and reviews should not be destroyed automatically.

# 23. Security Requirements

- Never store plain-text passwords.
- Never return password hashes.
- Never allow public registration as ADMIN.
- Never trust role information supplied by the frontend after authentication.
- Validate JWT signatures.
- Validate JWT expiration.
- Check that the authenticated user still exists and is active.
- Enforce ownership on profile updates.
- Use parameterized SQL queries.
- Validate all request bodies.
- Validate uploaded files.
- Do not expose database errors to clients.
- Keep JWT secrets in environment variables.
- Keep database credentials in environment variables.
- Keep Supabase credentials in environment variables.
- Never commit `.env` files.

---

# 24. Transaction Requirements

Use PostgreSQL transactions when multiple related records must be created or updated together.

Registration must be atomic.

For example:

```text
BEGIN

Create user
Create customer/worker profile

COMMIT
```

If profile creation fails:

```text
ROLLBACK
```

Do not leave orphaned users without their required role profile.

# 25. Testing Requirements

Create tests for the most important user/authentication scenarios.

### Registration

- Customer registration succeeds.
- Worker registration succeeds.
- Admin registration is rejected.
- Duplicate email is rejected.
- Duplicate phone is rejected where applicable.
- Invalid email is rejected.
- Weak password is rejected.
- Invalid role is rejected.
- Invalid language is rejected.
- Worker is created with `PENDING` approval status.
- Customer profile is created automatically.
- Worker profile is created automatically.
- Registration transaction rolls back on failure.

### Login

- Valid credentials succeed.
- Invalid password fails.
- Unknown email fails.
- Inactive user cannot log in.
- Valid JWT is returned.

### Authentication

- Missing token returns 401.
- Invalid token returns 401.
- Expired token returns 401.
- Active authenticated user can access `/users/me`.

### Authorization

- Customer cannot access worker-only APIs.
- Worker cannot access customer-only APIs.
- Customer cannot update another user's profile.
- Worker cannot modify approval status.
- Non-admin cannot perform admin operations.

### Password

- Correct current password allows password change.
- Incorrect current password is rejected.
- New password is securely hashed.
